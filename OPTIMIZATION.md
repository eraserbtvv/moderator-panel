# Оптимизация медиатеки (`src/pages/PhotosPage.tsx`) и разделение кода (`src/App.tsx`)

Масштаб проблемы до правок: 5000 строк × `simulateHeavyRender()` (0,05 мс) ≈ **250 мс
только на «дорогую» часть рендера строк**, плюс создание и сравнение 5000 DOM-узлов,
фильтрация и сортировка. И всё это происходило при любом изменении состояния страницы:
каждую секунду, на каждую букву в поиске, на каждый клик «В избранное».

После правок в DOM ~14 строк (видимые + запас), таймер и клики по избранному
перерисовывают только то, что действительно изменилось.

---

## 1. Таймер «Вы на странице N с» перерисовывал всю страницу каждую секунду

**Что происходило.** `secondsOnPage` лежал в состоянии `PhotosPage`. Раз в секунду
`setInterval` менял его, и React перерисовывал весь компонент страницы вместе со всеми
5000 строками. Поэтому страница «лагала, даже когда вы ничего не делаете»: раз в секунду
основной поток был занят ~250+ мс.

**Как исправлено.** Таймер вынесен в отдельный компонент `SecondsOnPage` со своим
состоянием. Теперь ежесекундное обновление перерисовывает только один `<p>`.

**Почему так.** Это «спуск состояния вниз» (state colocation): состояние живёт там,
где используется. Альтернатива — обернуть список в `memo` и оставить таймер в родителе —
хуже: родитель всё равно рендерился бы каждую секунду, заново считал бы фильтрацию
и сравнивал пропсы; к тому же это лечит симптом, а не причину.

## 2. Рендерились все 5000 строк, хотя видно ~9

**Что происходило.** `visiblePhotos.map(...)` создавал 5000 компонентов `PhotoRow`
(каждый со `simulateHeavyRender()`) и 5000 DOM-узлов, хотя контейнер `.photo-list`
высотой 500 px показывает около 9 строк по 56 px. Первый рендер, любой ре-рендер,
фильтрация и сортировка — всё платило за 5000 строк.

**Как исправлено.** Список вынесен в компонент `PhotoList` и виртуализирован через
`useVirtualizer` из `@tanstack/react-virtual`: внутри скролл-контейнера — «распорка»
высотой `getTotalSize()`, а в DOM только видимые строки плюс `overscan: 5`,
позиционированные через `transform: translateY(...)`. Высота строки (56 px) совпадает
с `.photo-row` из CSS, поэтому внешний вид не изменился. `getItemKey` возвращает
`photo.id`, чтобы при фильтрации React переиспользовал строки по id, а не по индексу.

**Почему так.** Строки фиксированной высоты — идеальный случай для виртуализации: без
замеров, с точным `estimateSize`. Пагинация или «показать ещё» изменили бы поведение
страницы (запрещено условием), а `memo` без виртуализации не спасает первый рендер
и смену фильтра — всё равно 5000 строк. Библиотека уже установлена, условие просит её.

## 3. Фильтрация и сортировка 5000 записей на каждом рендере

**Что происходило.** `visiblePhotos` считался прямо в теле компонента: два `filter`
и `sort` при каждом рендере — в том числе от таймера и от клика «В избранное», которые
на результат не влияют. `sort` — O(n log n) ≈ 60 000 сравнений, причём
`String.prototype.localeCompare` без аргументов на каждом вызове заново разбирает
настройки локали. Ещё `query.toLowerCase()` вызывался внутри `filter` 5000 раз.

**Как исправлено.**
- Сортировка вынесена в отдельный `useMemo([photos, sortOrder])` — пересчитывается только
  при загрузке данных и смене порядка, а не на каждую букву поиска.
- Фильтрация — во втором `useMemo([sortedPhotos, albumId, deferredQuery])`, поверх
  уже отсортированного массива (фильтр сохраняет порядок, результат тот же). Оба условия
  проверяются за один проход, `query.toLowerCase()` и `Number(albumId)` — один раз.
- Вместо `localeCompare` используется один общий `Intl.Collator` (`titleCollator.compare`).
  Результат сравнения тот же, но объект локали создаётся один раз, а не на каждое сравнение.
- Для «Я–А» оставлен обратный компаратор, а не `reverse()`, чтобы порядок строк
  с одинаковыми названиями совпадал с исходным.

**Почему так.** `useMemo` — штатный способ не пересчитывать производные данные, пока
не изменились входные. Разделение на две мемоизации важно: самая дорогая операция
(сортировка) не зависит от поиска, и набор букв её больше не запускает. Хранить
отфильтрованный список в `useState` + `useEffect` было бы хуже: лишний рендер
и риск рассинхронизации.

## 4. Поле поиска «тормозило» при вводе

**Что происходило.** Каждое нажатие клавиши синхронно запускало фильтрацию и ре-рендер
списка; пока они не закончатся, браузер не мог отрисовать введённую букву.

**Как исправлено.** Для фильтрации используется `useDeferredValue(query)`. Поле ввода
обновляется сразу (срочное обновление), а пересчёт списка идёт с низким приоритетом
и прерывается, если пользователь продолжает печатать.

**Почему так.** Debounce добавил бы фиксированную задержку даже на быстрых устройствах
и изменил бы ощущение от страницы (результат всегда запаздывает на N мс).
`useDeferredValue` не меняет логику — список фильтруется по тому же запросу — а только
приоритизирует ввод; на быстром устройстве задержки нет вовсе. Вместе с виртуализацией
и мемоизацией (п. 2–3) отложенная часть работы стала маленькой.

## 5. «В избранное» перерисовывал все строки

**Что происходило.**
- `handleToggleFavorite` создавался заново на каждом рендере, поэтому у каждой строки
  менялся проп `onToggleFavorite`, и даже `memo` не помог бы.
- `PhotoRow` не был обёрнут в `memo`, так что клик по одной кнопке перерисовывал
  все строки со `simulateHeavyRender()`.
- Обработчик читал `favorites` из замыкания — при быстрых кликах можно было потерять
  обновление из-за устаревшего значения.

**Как исправлено.** `PhotoRow` обёрнут в `React.memo`. `handleToggleFavorite` —
`useCallback` с пустыми зависимостями и функциональным обновлением
`setFavorites(prev => ...)`, поэтому ссылка стабильна и всегда работает с актуальным
состоянием. Теперь при клике перерисовывается только строка, у которой изменился
`isFavorite`.

**Почему так.** `memo` работает только при стабильных пропсах, поэтому `memo`
и `useCallback` нужны вместе: по отдельности каждый из них бесполезен. Функциональное
обновление позволяет не указывать `favorites` в зависимостях `useCallback`
(иначе ссылка менялась бы после каждого клика).

## 6. Проверка избранного за O(n) для каждой строки

**Что происходило.** `favorites` был массивом, и для каждой строки вызывался
`favorites.includes(photo.id)` — линейный поиск. На 5000 строк и сотню избранных
это сотни тысяч сравнений на рендер; `handleToggleFavorite` тоже делал `includes`
и `filter`.

**Как исправлено.** `favorites` хранится как `Set<number>`: проверка `has` — O(1).
При изменении создаётся новый `Set` (иммутабельно, чтобы React увидел изменение).
Счётчик «В избранном» берёт `favorites.size`.

**Почему так.** `Set` — естественная структура для «множества id», поведение и внешний
вид не меняются. Альтернатива `Record<number, true>` работает так же, но хуже
читается и требует ручного подсчёта размера.

## Разделение кода (задача 7)

**Что происходило.** Все страницы импортировались статически в `App.tsx`, поэтому
код медиатеки (вместе с `@tanstack/react-virtual`), страницы поста и остальных
попадал в один стартовый бандл — даже если пользователь открыл только список постов.

**Как исправлено.** Страницы подключены через `React.lazy(() => import(...))`.
Для них заведён промежуточный layout-маршрут `<Suspense fallback={<Loader />}><Outlet /></Suspense>`,
вложенный внутрь `<Layout />`. Пока грузится чанк страницы, `Suspense` показывает
«Загружаем страницу...» на месте контента, а шапка с навигацией остаётся на экране.

**Почему так.** Если обернуть в `Suspense` весь `<Routes>`, при загрузке любого чанка
пропадала бы и шапка. Граница внутри `Layout`, вокруг `Outlet`, заменяет только
изменяющуюся часть. Вложенный маршрут без `path` позволяет сделать это в `App.tsx`,
не меняя `Layout` и не оборачивая каждую страницу отдельно.

**Результат `npm run build`:** в `dist/assets` появились отдельные чанки
`PostsPage-*.js`, `PostPage-*.js`, `UsersPage-*.js`, `PhotosPage-*.js`
(в нём же `@tanstack/react-virtual`), `NotFoundPage-*.js`, а также общий
`useFetch-*.js`, который Vite вынес, потому что его используют несколько страниц.
